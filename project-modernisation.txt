1. REPOSITORY STRUCTURE — PRODUCTION STANDARDS
================================================================================

Current State: Single-env flat layout. Not production-ready for multi-env.

GAPS:
  - terraform/ is flat — no module separation, no per-env workspace isolation
  - backend-infrastructure.tf (state bucket) lives alongside app infra — should
    be bootstrapped separately as its own module
  - No modules/ directory for reusable Terraform components
  - No environments/ directory for env-specific var files
  - .terraform.lock.hcl is gitignored — SHOULD be committed (reproducible installs)
  - No .terraform-version or .tool-versions for toolchain version pinning
  - No Makefile / justfile as a developer task runner
  - No tests/ directory (Terratest, checkov, tfsec)
  - No docs/ directory for runbooks and architecture diagrams

RECOMMENDED STRUCTURE:
  /
  ├── environments/
  │   ├── dev/
  │   │   ├── backend.hcl          ← gitignored, per-env backend secrets
  │   │   └── terraform.tfvars     ← gitignored, per-env variable values
  │   └── stg/
  │       ├── backend.hcl
  │       └── terraform.tfvars
  ├── terraform/
  │   ├── modules/
  │   │   ├── static-site/         ← reusable S3 + CloudFront module
  │   │   └── state-backend/       ← bootstrap module (run once per account)
  │   ├── main.tf
  │   ├── variables.tf
  │   ├── outputs.tf
  │   ├── providers.tf
  │   ├── locals.tf                ← NEW: common locals + merged tags
  │   ├── backend.tf
  │   └── .terraform.lock.hcl     ← COMMITTED (remove from .gitignore)
  ├── docs/
  │   └── architecture.md          ← Mermaid diagram of full system
  ├── tests/
  │   └── checkov/                 ← IaC security policy tests
  ├── .tool-versions               ← terraform 1.5.x, awscli 2.x
  └── example.tfvars.example       ← template since real tfvars is gitignored

3. HOOKS — ISSUES & FIXES
================================================================================

CRITICAL ISSUES:

  Hook / File                        | Problem
  -----------------------------------|------------------------------------------
  settings.json (all 3 hook paths)   | Hardcoded to S:/devops/... — breaks on
                                     | any machine other than the original dev box
  post-tool-logger.sh                | Deploy log path hardcoded to S:/devops/...
  pre-tool-guard.sh                  | Debug log hardcoded to /c/Users/raj/hook-debug.log
                                     | (personal username leaked into version control)
  All 3 hooks                        | No graceful fallback if jq not installed —
                                     | will fail silently
  All hooks                          | No PostToolUse hook for S3 sync operations
                                     | (only terraform apply is logged)
  All hooks                          | No notification hook on deployment completion
  user-prompt-guard.sh               | Silent pass on empty prompt is correct
                                     | behavior but should log the invocation

FIX STRATEGY:
  1. Replace all absolute paths in settings.json hook commands with:
       bash "$(git rev-parse --show-toplevel)/.claude/hooks/hook-name.sh"
     This makes the project portable to any machine or path.

  2. Add jq guard at top of every hook script:
       command -v jq >/dev/null 2>&1 || exit 0

  3. Replace hardcoded deploy log path in post-tool-logger.sh:
       LOG_DIR="$(git rev-parse --show-toplevel)/.claude"
       echo "[...]" >> "$LOG_DIR/deploy.log"

  4. Replace hardcoded debug log path in pre-tool-guard.sh:
       DEBUG_LOG="${TMPDIR:-/tmp}/claude-hook-debug.log"

  5. Add PostToolUse hook for S3 sync operations:
       Trigger on: aws s3 sync
       Log: timestamp, environment, bucket, file count, deployer identity

  6. Add set -euo pipefail to all hook scripts to catch silent failures.

  7. (Optional) Add a notification hook that fires on deployment success,
     posting to a webhook (Slack, Teams, PagerDuty).

5. DEV + STG ENVIRONMENTS — FULL PLAN
================================================================================

YES, fully achievable. Recommended approach: DIRECTORY-PER-ENVIRONMENT
(not Terraform workspaces).

WHY NOT TERRAFORM WORKSPACES:
  Workspaces share the same Terraform codebase and AWS provider credentials.
  For two different AWS accounts, directory isolation is cleaner, provides
  blast-radius separation, and allows independent state backends per account.

ARCHITECTURE OVERVIEW:
  Two AWS Accounts:
    Account A (DEV):  <dev-account-id>
    Account B (STG):  <stg-account-id>

  Two GitHub branches:
    release-dev  →  deploys to Account A (DEV)
    release-stg  →  deploys to Account B (STG)

  Two OIDC trust policies:
    Account A IAM Role: {project}-dev-github-deploy
      trusted: repo:{owner}/{repo}:ref:refs/heads/release-dev
    Account B IAM Role: {project}-stg-github-deploy
      trusted: repo:{owner}/{repo}:ref:refs/heads/release-stg

  Two Terraform state backends:
    s3://terraform-state-{devAccountId}-us-east-1
      key = {project}/dev/terraform.tfstate
    s3://terraform-state-{stgAccountId}-us-east-1
      key = {project}/stg/terraform.tfstate

  Two GitHub workflow files:
    .github/workflows/deploy-dev.yml   (trigger: push to release-dev)
    .github/workflows/deploy-stg.yml   (trigger: push to release-stg)

TERRAFORM VARIABLE FILES:
  environments/dev/terraform.tfvars:
    region        = "us-east-1"
    project_name  = "agenticai"
    environment   = "dev"
    aws_account   = "<dev-account-id>"
    github_branch = "release-dev"
    cost_center   = "CC-001-DEV"
    owner_team    = "platform-team"

  environments/stg/terraform.tfvars:
    region        = "us-east-1"
    project_name  = "agenticai"
    environment   = "stg"
    aws_account   = "<stg-account-id>"
    github_branch = "release-stg"
    cost_center   = "CC-001-STG"
    owner_team    = "platform-team"

TERRAFORM INIT PER ENVIRONMENT:
  # DEV
  cd terraform
  terraform init -backend-config=../environments/dev/backend.hcl
  terraform plan -var-file=../environments/dev/terraform.tfvars

  # STG
  cd terraform
  terraform init -backend-config=../environments/stg/backend.hcl
  terraform plan -var-file=../environments/stg/terraform.tfvars

ADD TO terraform/variables.tf:
  variable "owner_team" {
    description = "Team responsible for this environment"
    type        = string
  }
  variable "cost_center" {
    description = "Billing cost center code"
    type        = string
  }
  variable "github_repo" {
    description = "GitHub repository (owner/name) for OIDC trust"
    type        = string
  }
  variable "github_branch" {
    description = "GitHub branch scoped in OIDC trust condition"
    type        = string
  }
  variable "aws_account" {
    description = "Target AWS account ID (used for validation)"
    type        = string
  }
  variable "cloudfront_price_class" {
    description = "CloudFront price class (PriceClass_100 is cheapest)"
    type        = string
    default     = "PriceClass_100"
    validation {
      condition     = contains(["PriceClass_100","PriceClass_200","PriceClass_All"], var.cloudfront_price_class)
      error_message = "Must be PriceClass_100, PriceClass_200, or PriceClass_All"
    }
  }

TWO AWS ACCOUNTS — PROVIDER PATTERN:
  Each environment's pipeline authenticates via OIDC into the correct account.
  No alias provider needed in single-env Terraform runs.
  The aws_account variable can be used with a data source check:
    data "aws_caller_identity" "current" {}
    locals {
      account_check = var.aws_account != "" && data.aws_caller_identity.current.account_id != var.aws_account ? tobool("ERROR: wrong AWS account") : true
    }
  This prevents accidentally applying DEV terraform against the STG account.

19. COMMIT TAGGING STRATEGY
================================================================================

FORMAT: release-{env}-SHA-{git_sha_short_7_chars}
  Examples:
    release-dev-SHA-a1b2c3d   ← DEV deploy of commit a1b2c3d
    release-stg-SHA-e4f5g6h   ← STG deploy of commit e4f5g6h

IMPLEMENTATION IN GITHUB ACTIONS (post-verify step):
  - name: Tag release
    run: |
      TAG="release-${{ env.ENVIRONMENT }}-SHA-${GITHUB_SHA::7}"
      git config user.name  "github-actions[bot]"
      git config user.email "github-actions[bot]@users.noreply.github.com"
      git tag -a "$TAG" -m "Deploy to ${{ env.ENVIRONMENT }} from ${GITHUB_SHA}"
      git push origin "$TAG"

CROSS-REPOSITORY TRACEABILITY:
  When UI and infra are separate repos, both produce matching tags:
    agenticai-ui    commit release-dev-SHA-a1b2c3d  → UI files deployed to DEV
    agenticai-infra commit release-dev-SHA-e4f5g6h  → Terraform applied to DEV

  The release-dev branch in each repo always reflects what is live in DEV.
  Tags are permanent, searchable, and link back to exact code + infra state.

INFRASTRUCTURE VERSIONING:
  Terraform state already versions infrastructure state in S3.
  Each git tag on the infra repo maps to an exact terraform.tfstate snapshot.
  Combined: code tag + infra tag + S3 state version = full audit trail.

20. MULTI-STAGE PIPELINE + DEVSECOPS
================================================================================

PROPOSED PIPELINE ARCHITECTURE (per environment workflow):

  Job 1: validate
    Runs on: every push
    Steps:
      - terraform fmt -check         ← formatting gate
      - terraform validate           ← syntax gate
      - checkov --dir terraform/     ← IaC security policy gate
      - gitleaks detect              ← secret scanning gate
    On failure: block all subsequent jobs

  Job 2: security-scan (parallel with validate)
    Steps:
      - tfsec terraform/             ← Terraform security linting
      - HTML link checker (optional) ← UI quality gate

  Job 3: plan (needs: validate)
    Steps:
      - terraform init -backend-config
      - terraform plan -out=tfplan.binary -var-file=environments/{env}/terraform.tfvars
      - Upload tfplan.binary as GitHub Actions artifact
      - Post plan summary as PR comment (using tfcmt or custom script)

  Job 4: approve (needs: plan, security-scan)
    DEV:  auto-approved (no gate)
    STG:  GitHub Environment "stg" with required reviewer rule
          Reviewer must approve before Job 5 runs

  Job 5: deploy (needs: approve)
    Steps:
      - Download tfplan.binary artifact  ← apply exactly what was reviewed
      - terraform apply tfplan.binary    ← no fresh plan, no drift between review/apply
      - aws s3 sync to S3 bucket         ← site content deploy
      - aws cloudfront create-invalidation ← cache flush

  Job 6: verify (needs: deploy)
    Steps:
      - HTTP smoke test: curl -f https://{cloudfront_url} → expect 200
      - terraform output validation (check outputs exist)
      - aws cloudfront get-distribution → verify status = Deployed

  Job 7: tag-and-notify (needs: verify)
    Steps:
      - git tag release-{env}-SHA-{sha} and push
      - Notify Slack/email: deploy successful, URL, tag, deployer identity
    On failure of any previous job:
      - Notify Slack/email: deploy FAILED, job name, error summary

NOTES ON CURRENT SINGLE-STEP S3 SYNC:
  Current deploy.yml does aws s3 sync in one step with no validation before
  or verification after. This means:
    - A broken HTML file will deploy silently
    - No confirmation the site is actually responding after deploy
    - No record of what changed (no --dryrun first)
  Multi-stage fixes all three.

21. SEPARATE CODE & INFRASTRUCTURE REPOSITORIES
================================================================================

RECOMMENDED SPLIT FOR MINIMUM BLAST RADIUS:

  Repo 1: agenticai-ui (Code Repository)
    Responsibility: All site content — HTML, CSS, images, static assets
    Owns: S3 sync and CloudFront invalidation workflows
    Does NOT own: Terraform, IAM, infrastructure provisioning
    Who merges: Frontend/UI engineers, reviewed by content owners
    Branch strategy:
      main         → source of truth
      release-dev  → triggers deploy to DEV S3 bucket
      release-stg  → triggers deploy to STG S3 bucket
    OIDC Role permissions: s3:Put/Get/Delete/List, cloudfront:CreateInvalidation

  Repo 2: agenticai-infra (Infrastructure Repository)
    Responsibility: All AWS infrastructure via Terraform, all AI automation
    Owns: terraform/, .claude/, .github/workflows/infra-*.yml
    Does NOT own: site content files
    Who merges: Platform/DevOps engineers, reviewed by security team
    Branch strategy:
      main         → source of truth
      release-dev  → triggers infra-dev.yml (plan + apply to DEV account)
      release-stg  → triggers infra-stg.yml (plan + apply to STG account)
    OIDC Role permissions: Full Terraform permissions (S3, CF, IAM, DynamoDB)

BLAST RADIUS BENEFITS:
  - A bad HTML commit cannot affect infrastructure state
  - A Terraform change cannot accidentally overwrite site content
  - OIDC roles are least-privilege per repo — UI repo cannot touch state bucket
  - Independent deploy cadences: site can deploy 10x per day, infra 1x per week
  - Separate code review processes and approval gates per domain
  - Separate access controls: UI repo is less sensitive than infra repo

COORDINATION FOR FIRST-TIME SETUP:
  1. Provision infrastructure first using agenticai-infra repo
  2. agenticai-infra terraform output → bucket name + distribution ID
  3. Set those values as GitHub vars in agenticai-ui repo
  4. UI repo's workflows now have the targets they need
